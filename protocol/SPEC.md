# Carom protocol, version 1

This is the contract between the Hub (Cloudflare Worker + Durable Object) and every
client (Android, macOS, future CLI). The test vectors in `vectors/` are normative:
every implementation must pass them.

Key words: MUST, SHOULD, MAY as in RFC 2119.

## 1. Conventions

- `b64` means base64url **without padding** (RFC 4648 §5). All binary values in JSON use it.
- Times are Unix epoch **milliseconds** unless the field name ends in `_s` (seconds).
- Strings are UTF-8.
- `lp(x)` is length-prefixed bytes: `u32be(len(x)) || x`. Strings are encoded as UTF-8 first.
- `u64(n)` is an 8-byte big-endian unsigned integer.
- `||` is concatenation.
- Inside `lp(…)`, binary values (keys, salts, ciphertexts, MACs, signatures) are always the
  **raw bytes**, never their b64 text. Device ids, `msg_id`, `pair_id` and tags are UTF-8 text.
- "Sorted ascending" means by the UTF-8 bytes of the id.
- Ed25519 verification is strict RFC 8032 (canonical `S`, as CryptoKit does), not ZIP-215.

## 2. Cryptography

All primitives exist natively or in a mainstream library on each platform:
CryptoKit (macOS), Tink or BouncyCastle (Android), `@noble/*` (TypeScript reference).
No libsodium is required.

| Purpose | Primitive |
|---|---|
| Signatures | Ed25519 (RFC 8032) |
| Key agreement | X25519 (RFC 7748) |
| Key derivation | HKDF-SHA256 (RFC 5869) |
| MAC | HMAC-SHA256 |
| AEAD | ChaCha20-Poly1305, IETF (RFC 8439), always used with a **single-use key** and an all-zero 12-byte nonce |
| Hash | SHA-256 |

Each AEAD key is derived per message from a fresh 32-byte random salt, so a key is never
used twice and a zero nonce is safe. This gives the nonce-misuse margin of XChaCha20
without needing it.

Ed25519 signers MAY be randomized (CryptoKit is). Vectors therefore check signatures
by **verification**. Byte-exact signature checks are only done where signing is deterministic.

### 2.1 Keys

| Key | Size | Held by | Purpose |
|---|---|---|---|
| Identity signing key `sign_sk/sign_pub` | Ed25519 | each device | signs envelopes, records |
| Key-agreement key `kx_sk/kx_pub` | X25519 | each device | receives the group key |
| Group key `K` with version `kv` (u32, starts at 1) | 32 random bytes | all devices of one owner | encrypts payloads and records |
| Device token | 32 random bytes | device + Hub (hashed) | transport auth only |
| Pair secret | 32 random bytes | pairing QR only | authenticates one pairing |

Derived from `K`:

```
msg_key(K, salt)  = HKDF(ikm=K, salt=salt, info="carom/v1/msg", L=32)
K_collapse(K)     = HKDF(ikm=K, salt="",   info="carom/v1/collapse", L=32)
```

### 2.2 Device id

A device id is derived from the signing key, so the Hub cannot pair an id with a different key:

```
device_id = "dev_" || b64(SHA-256(sign_pub)[0..16])      // 4 + 22 chars
```

Every receiver MUST recompute and check this whenever it sees a `(id, sign_pub)` pair.

### 2.3 Seal (group-key encryption + signature)

Envelopes and device records both use *seal*. Inputs: the domain tag `tag`, the
ordered header fields `H` (a list of byte strings), the plaintext `P`, the group key
`K`, its version `kv`, and the sender's `sign_sk`.

```
salt = random(32)
aad  = lp(tag) || lp(H[0]) || lp(H[1]) || ... || lp(u64(kv)) || lp(salt)
ct   = ChaCha20-Poly1305-Encrypt(key=msg_key(K, salt), nonce=0^12, aad=aad, pt=P)
sig  = Ed25519-Sign(sign_sk, aad || lp(ct))
```

To open, rebuild `aad` from the received fields. Then:

1. Verify `sig` with the sender's `sign_pub`, and reject on failure.
2. Look up `K` by `kv`, and reject if it is unknown.
3. Decrypt, and reject on failure.

### 2.4 Box (encrypt to one device's X25519 key)

Used for the pairing welcome and for rekeying. `psk` is optional and empty by default.

```
(eph_sk, eph_pub) = X25519 keygen
ss   = X25519(eph_sk, rcpt_kx_pub)        // reject if all-zero
key  = HKDF(ikm=ss || psk, salt=eph_pub || rcpt_kx_pub, info="carom/v1/box", L=32)
ct   = ChaCha20-Poly1305-Encrypt(key, nonce=0^12, aad=aad, pt=P)
box  = { "epk": b64(eph_pub), "ct": b64(ct) }
```

`aad` is defined by each use.

## 3. Envelope

The Hub routes the envelope. Only devices can read its payload.

```json
{
  "v": 1,
  "msg_id": "01928f3c-7b1e-7c4a-9d2f-5e8a1b2c3d4e",
  "from": "dev_…",
  "to": ["dev_…"],
  "collapse": "Zp3kQ…",
  "ttl_s": 172800,
  "kv": 1,
  "salt": "b64(32 bytes)",
  "ct": "b64",
  "sig": "b64(64 bytes)"
}
```

| Field | Rules |
|---|---|
| `v` | `1` |
| `msg_id` | lowercase UUIDv7 string, generated by the sender. The idempotency key. |
| `from` | the sender's device id. The Hub MUST check it equals the authenticated device. |
| `to` | 1–32 distinct device ids, not including `from` |
| `collapse` | optional; when present, b64 of exactly 16 bytes (see §3.2). When absent, it is encoded as the empty string in the AAD. An empty string in JSON is invalid. |
| `ttl_s` | 60 … 604800 |
| `kv`, `salt`, `ct`, `sig` | as described in §2.3 |

Seal header fields, in this order, with `tag = "carom/v1/env"`:

```
H = [ u64(v), msg_id, from, to_joined, collapse_or_empty, u64(ttl_s) ]
to_joined = lp(to[0]) || lp(to[1]) || ...      (in the order sent)
```

Size limits: the (padded) plaintext payload is at most 65 536 bytes, and the envelope
serialized as compact JSON is at most 98 304 bytes. The Worker also caps the raw request body. Larger content will use `blob.ref@1` (phase 2).

### 3.1 Payload (plaintext inside `ct`)

```json
{ "type": "clipboard.set@1", "ts": 1791648000000, "reply_to": "uuid?", "body": { … } }
```

`ts` is the sender's clock at send time. `reply_to` always sits at payload level, never in `body`.

Senders SHOULD pad the payload JSON with trailing ASCII spaces (JSON allows trailing
whitespace). Pad to a multiple of 256 bytes below 4096, and a multiple of 4096 above that.
This hides exact lengths from the Hub. The padded length still has to fit the plaintext limit.
Examples: 0 stays 0, 1 becomes 256, 4096 stays 4096, and 4097 becomes 8192.

`msg_id` MUST be UUIDv7 and monotonic per sender (RFC 9562 §6.2 method 1 or 3).
The Hub relies on this for collapse ordering.

### 3.2 Collapse

```
collapse = b64( HMAC-SHA256(K_collapse(K), lp(from) || lp(real_key))[0..16] )
```

The Hub keeps at most one message per `(from, collapse)`. A newer message deletes the
older one and every pending delivery of it, even for recipients that are not in the new
`to`. Acks for a seq that no longer exists succeed silently.

"Newer" means a greater `msg_id` (UUIDv7 order). If the incoming `msg_id` is lower than the
stored one, the Hub answers `200 {seq: null, superseded: true}` and stores nothing. This
stops a late retry from overwriting a fresher clipboard item.

Collapse values depend on `kv`, so a message sent before a rekey is not replaced by one
sent after it. This is harmless. Real keys used in v1:

- `clip` for clipboard
- `n:<android notification key>` for notification posted/removed, which share one slot so
  a removal replaces the pending post
- `status` for device status

### 3.3 Receiver rules

Apply these in order. The first failure drops the message silently (log it locally) and still acknowledges it.

1. The receiver's own id is in `to`. A Hub must not be able to redirect messages.
   `from` is in the local trusted directory (§5.3), and `device_id(sign_pub)` matches.
2. The signature verifies, `kv` is known, and decryption succeeds.
3. `now - ts <= ttl_s*1000 + 300000` and `ts - now <= 300000` (5 minutes of clock skew).
4. `msg_id` has not been seen before. Receivers remember seen ids for 7 days plus the skew.
5. The type is known (`caps`). Unknown types are acknowledged and ignored. A known type
   whose body fails its schema is dropped (`bad_payload`).
6. For `clipboard.set`: ignore it if `ts` is older than the last clipboard item applied locally.
7. A message with `reply_to` is accepted only from a device that was in the `to` of the
   original message. The original sender knows this.

## 4. Message types (v1)

The JSON Schemas are in `schemas/`. Additive fields do not bump `@major`, and receivers
MUST ignore unknown fields.

| Type | Body | Default TTL | Collapse |
|---|---|---|---|
| `notification.posted@1` | `key, app{id,name}, title?, text?, sub_text?, category?, posted_at, redacted, ongoing?` | 2 days | `n:<key>` |
| `notification.removed@1` | `key` | 2 days | `n:<key>` |
| `notification.dismiss@1` | `key`, with `reply_to` set to the posted message's msg_id | 1 day | none |
| `clipboard.set@1` | `mime` (`text/plain`), `text`, `sensitive` (bool), `source?` | 1 day | `clip` |
| `device.status@1` | `battery?` (0–100), `charging?` | 1 day | `status` |

Notification text is plain text. Receivers MUST NOT render markup or auto-open URLs.

## 5. Devices, directory and trust

### 5.1 Device record (plaintext)

```json
{
  "id": "dev_…", "name": "Michał's Pixel", "kind": "phone",
  "platform": "android", "app_version": "1.0.0",
  "sign_pub": "b64", "kx_pub": "b64",
  "caps": ["notification.dismiss@1", "clipboard.set@1"],
  "receive": {
    "clipboard.set@1": "*",
    "notification.posted@1": ["dev_…"]
  },
  "updated": 1791648000000
}
```

`kind` is one of `phone`, `desktop`, `cli`. `receive` maps a type to either `"*"` (from
every device) or a list of allowed sender ids. A missing type means "do not send me this".

The record is sealed (§2.3) with `tag = "carom/v1/rec"` and `H = [id, u64(updated)]`.
The signer's key is inside the ciphertext, so a record is opened in this order:

1. Check that `kv` is the current key.
2. Decrypt and parse the record.
3. Check that the inner `id` and `updated` match the outer ones.
4. Check that `device_id(sign_pub) == id`.
5. Verify `sig`.
6. Reject a rollback.

The Hub can verify the signature directly, because it knows each device's `sign_pub`.

It is published as:

```json
{ "id": "dev_…", "updated": 1791648000000, "kv": 1, "salt": "…", "ct": "…", "sig": "…" }
```

Default `receive` written at pairing:

| Type | phone | desktop |
|---|---|---|
| `notification.posted@1`, `notification.removed@1`, `device.status@1` | — | `"*"` |
| `clipboard.set@1` | `"*"` | `"*"` |
| `notification.dismiss@1` | `"*"` (only replies to its own notifications arrive) | — |

A `cli` device receives only `clipboard.set@1` by default.

### 5.2 Routing

When sending type `T`, a device puts `D` in `to` when `D.receive[T]` is `"*"` or contains
the sender's id, `D` is not revoked, and `T` is in `D.caps`. Replies, meaning messages with
`reply_to`, go only to the original sender.

If the Hub answers `409 conflict` with `{"inactive": [ids]}`, the sender refetches the
directory, drops those ids, and re-seals the message under the **same** `msg_id`.

Local filters, such as ignored apps on the phone or muted apps on the Mac, are applied on
top of this and never leave the device.

### 5.3 Trust

A device is a member when all three of these hold:

- its record opens with the **current** group key,
- the record signature verifies with the `sign_pub` inside it, and
- `device_id(sign_pub) == id`.

The Hub never holds `K`, so it cannot add members. Records sealed under an older `kv` are
ignored, so a revoked device cannot be brought back with an old record. Receivers keep the
highest `updated` per id and ignore rollbacks. Records the device cannot open are ignored.

Identity keys are bound to the device. They MUST be excluded from backups and device
transfer: Android backup rules, and the macOS Keychain with
`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`. A reinstall means a new identity and a
new pairing.

### 5.4 Revocation

Any member may call `DELETE /v1/devices/:id`, including on itself. The Hub kills the token,
drops pending deliveries, sends `{"t":"revoked"}` to the device, and sends `dir` to everyone
else. The revoking device MUST then rekey (§5.5), so the revoked device cannot read future
messages.

Every other device shows a visible notice of the form "<revoker> removed <device>". A
device that disappears from the directory without a rekey is also flagged.

### 5.5 Rekey

Rekeying uses the Hub *keyring*, not a message. The keyring is never pruned by TTL, so a
device that was offline for weeks still gets the new key.

The rekeying device `R` generates a new `K'` and `kv' = kv + 1`. For each remaining
member `D` (including itself), it computes:

```
box_D = Box(rcpt=D.kx_pub, aad = lp("carom/v1/rekey") || lp(R.id) || lp(D.id) || lp(u64(kv')), P = K')
sig   = Ed25519(R.sign_sk, lp("carom/v1/rekey") || lp(R.id) || u64(kv') ||
                lp(D1.id) || lp(box_D1.epk) || lp(box_D1.ct) || …)   // ids sorted ascending
```

`R` then calls `PUT /v1/keyring` with `{kv, by: R.id, boxes: {id: box}, sig}`. The Hub
accepts this only if `kv` equals the newest keyring version + 1 (or 2 when the keyring is
empty, because kv 1 is created at setup and never stored there). Otherwise it answers 409. This
serializes concurrent rekeys. The Hub then sends `dir` to every device.

Each device calls `GET /v1/keyring?have=kv`. The response contains every version newer
than `kv`, with all boxes included so the signature can be checked. The device then:

1. Checks that `by` was a member under the previous key.
2. Verifies `sig` over all boxes.
3. Opens its own box.
4. Republishes its record under `K'`.

Old keys are kept for 7 days so queued messages can still be opened. New messages are always
sealed with the newest key.

## 6. Hub HTTP API

Base URL: the Hub URL, for example `https://carom-hub.<account>.workers.dev`. All bodies are
JSON. Authenticated routes need `Authorization: Bearer <token>`.

Errors use the form `{"error": {"code": "snake_case", "message": "…"}}`, with codes
`bad_request`, `unauthorized`, `forbidden`, `not_found`, `conflict`, `gone`, `too_large`
`rate_limited`, `unavailable` (503, for example a missing or too-short `SETUP_TOKEN`) and
`internal` (500).

| Method + path | Auth | Request → Response |
|---|---|---|
| `GET /v1/info` | none | → `{name:"carom-hub", protocol:1, version, setup_done, vapid_public_key, jurisdiction}`. `vapid_public_key` is b64 of the uncompressed P-256 point. |
| `POST /v1/setup` | none | `{setup_token, sign_pub, kx_pub}` → `{device_id, token}`. Only works once. |
| `PUT /v1/keyring` | device | `{kv, by, boxes, sig}` → `{}`, or 409 if `kv` is not current+1 |
| `GET /v1/keyring?have=N` | device | → `{versions:[{kv, by, sig, boxes:{id:{epk,ct}}}]}` with every box of each newer version |
| `POST /v1/reset` | none | `{setup_token, confirm:"erase everything"}` → `{}`. Wipes all state, and setup is possible again. |
| `POST /v1/pair/offer` | device | `{}` → `{pair_id, expires_at}` (5 minutes) |
| `GET /v1/pair/:pair_id` | offerer | → `{status:"waiting"\|"accepted"\|"done", candidate?:{device_id, sign_pub, kx_pub, mac, pop}}` |
| `POST /v1/pair/accept` | none | `{pair_id, sign_pub, kx_pub, mac, pop}` → `{device_id, token}`. The device is *pending*. |
| `POST /v1/pair/:pair_id/welcome` | offerer | `{box}` → `{}`. Activates the candidate. |
| `POST /v1/pair/:pair_id/reject` | offerer | → `{}`. Deletes the candidate. |
| `GET /v1/pair/:pair_id/welcome` | candidate (pending or just activated) | → `{box}`, or 404 `not_found` while waiting. After the welcome is posted, the pairing stays readable for another 5 minutes. |
| `GET /v1/devices` | device | → `{devices:[{id, sign_pub, kx_pub, created_at, last_seen, has_push, record?}]}` |
| `PUT /v1/devices/self/record` | device | `{record}` → `{}` |
| `PUT /v1/devices/self/push` | device | `{endpoint, p256dh, auth}` → `{}` |
| `DELETE /v1/devices/self/push` | device | → `{}` |
| `DELETE /v1/devices/:id` | device | → `{}`. Revokes the device. `self` is allowed. |
| `POST /v1/messages` | device | `{envelope}` → `{seq, duplicate}` |
| `GET /v1/messages?limit=N` | device | → `{messages:[{seq, envelope}], more}` (unacknowledged, in `seq` order, N ≤ 200) |
| `POST /v1/acks` | device | `{up_to: seq}` → `{}` (cumulative: everything ≤ `up_to` addressed to this device is acknowledged) |
| `GET /v1/ws` | device | WebSocket upgrade, see §7 |

A pending device can only call `GET /v1/pair/:pair_id/welcome`. Every other route returns 403.
`pair_id` is b64 of 16 random bytes (22 characters).

`seq` is strictly increasing and is never reused, even after the newest message is
collapsed away. A superseded post returns `{seq: null, duplicate: false, superseded: true}`.

Rules the Hub enforces on `POST /v1/messages`:

1. Strict shape and size limits, and `ttl_s` bounds.
2. `from` equals the caller, and the caller is active.
3. `sig` verifies with the caller's stored `sign_pub`. This is defence in depth; Workers
   WebCrypto supports Ed25519.
4. Every `to` id is active. Otherwise the Hub answers `409 {"error":…, "inactive":[ids]}`.
5. `(from, msg_id)` is unique for as long as the message's TTL lasts, even after every
   recipient has acknowledged it. Acknowledged messages are reduced to tombstones (the envelope
   is dropped) until `expires_at`. A duplicate returns the original `seq` with `duplicate:true`.
6. Each recipient may have at most 1000 pending messages. Beyond that the post is refused with
   `429 rate_limited` and `{"full": [ids]}`. Collapse keeps normal use far below this.
7. The collapse rule from §3.2, which also compares against tombstones.

The Hub never decrypts `ct` and never branches on message type.

Tokens have the form `ct1.<device_id>.<b64 rand32>.<b64 mac16>`, where:

```
token_key = HKDF(ikm=UTF8(SETUP_TOKEN), salt="", info="carom/v1/token-key", L=32)
mac16     = HMAC-SHA256(token_key, lp(device_id) || lp(rand32))[0..16]
```

The Worker checks the MAC before it touches the Durable Object, so garbage requests never
reach it. The Hub then checks that `SHA-256(token)` belongs to an active device, which
covers revocation and pending state. Tokens are returned once. Resetting the Hub with a new
`SETUP_TOKEN` invalidates every token.

The `SETUP_TOKEN` Worker secret must be at least 32 characters, otherwise setup is refused.
It is compared in constant time against its SHA-256. Once setup succeeds, `claimed=1` is
stored permanently. Only `POST /v1/reset`, which also needs `SETUP_TOKEN`, clears it.

Rate limits are enforced inside the Hub, which is single-threaded and so counts exactly:

- `/v1/setup` and `/v1/reset`: after 10 failures in an hour, the route is locked for an hour.
- `/v1/pair/accept`: one accept per `pair_id`, and at most 5 open offers at a time.
- Push sends: at most one per recipient per message (see §9).

Push endpoints MUST be `https:` URLs on the default port, with a DNS hostname: not an IP literal, not
`localhost`, and not the Hub's own host (compared case-insensitively, ignoring a trailing dot).

## 7. WebSocket

`GET /v1/ws` with the bearer token. Ping: the client sends the text `ping` and the Hub
auto-responds `pong` without waking. Clients SHOULD ping every 30 seconds and reconnect
with jittered backoff (1 second doubling to 60 seconds).

Server → client frames:

- `{"t":"msg","seq":N,"envelope":{…}}`. On connect, the Hub sends the oldest unacknowledged
  messages, up to 100 messages or 1 MiB per page. Once an ack (a WebSocket frame or `POST /v1/acks`)
  covers the last `seq` of the page, it sends the next page, until the backlog is empty. While
  the backlog is paging, live messages are queued behind it. Clients ack the highest `seq`
  they have handled, and may also page with `GET /v1/messages`.
- `{"t":"dir"}`: the directory changed, so refetch `GET /v1/devices`.
- `{"t":"pair","pair_id":…,"candidate":{device_id, sign_pub, kx_pub, mac, pop}}`: sent to the offerer.
- `{"t":"revoked"}`: this device was revoked. Clients wipe their keys and close the socket
  themselves. The Hub also closes it with code 4001.

Clients MUST NOT wait for the server's half of a close handshake. Through the Cloudflare edge
the reply to a client-initiated close is not reliably delivered. Send the close frame, then
cancel the socket after at most 1 second (`URLSessionWebSocketTask.cancel`, OkHttp `cancel()`).

Client → server frames:

- `{"t":"ack","up_to":N}`: cumulative, same as `POST /v1/acks`.

Keep-alive: clients send WebSocket protocol pings (`URLSessionWebSocketTask.sendPing`,
OkHttp `pingInterval`) every 30 seconds. The runtime answers these without waking the
Hub. The text frame `ping` → `pong` is also auto-answered, for clients without
protocol pings.

## 8. Pairing

QR payloads are URIs. Apps also accept them as pasted text. Builders percent-encode every
character outside the RFC 3986 unreserved set, using uppercase hex. Parsers:

- require exactly the listed parameters,
- reject a raw `+` (it never means a space),
- trim surrounding whitespace,
- require `t` to be at least 32 characters, and
- require `h` to be `https:`. `http:` is allowed only for `localhost`, `127.0.0.1` and
  `[::1]`, for local development.

```
carom://setup?v=1&h=<urlenc hub url>&t=<setup token>
carom://pair?v=1&h=<urlenc hub url>&c=<pair_id>&s=<b64 pair_secret>
```

**First device (setup).** It generates its keys, calls `POST /v1/setup`, generates
`K` (`kv=1`), and publishes its record.

**Adding device B through member A:**

1. A calls `POST /v1/pair/offer`, generates `pair_secret`, and shows the QR code.
2. B scans the code, generates its keys, and computes:
   ```
   k_pair = HKDF(ikm=pair_secret, salt="", info="carom/v1/pair", L=32)
   mac    = HMAC(k_pair, lp("carom/v1/pair-req") || lp(pair_id) || lp(sign_pub) || lp(kx_pub))
   ```
   It also computes `pop = Ed25519(sign_sk, same bytes)` as proof of possession.
   B then calls `POST /v1/pair/accept` and stores the returned token. The pairing is
   single-use: the first accept consumes it.
3. A receives the candidate (a WebSocket `pair` frame, or by polling `GET /v1/pair/:id`)
   and checks `mac`, `pop` and `device_id`. `pop` is always present; a candidate without it is rejected. On a mismatch, A rejects and warns the user.
   A substituted key from a hostile Hub fails here. A also wipes `pair_secret` on use
   or after 5 minutes.
4. A sends `POST /v1/pair/:id/welcome` with:
   ```
   box = Box(rcpt=B.kx_pub, psk=k_pair,
             aad = lp("carom/v1/welcome") || lp(pair_id) || lp(B.id),
             P = JSON {"keys":[{"kv":1,"k":"b64"}, …], "inviter": A.id})
   ```
   Only a holder of `pair_secret` can produce this box, so B knows it came from A.
5. B polls `GET /v1/pair/:id/welcome` every 2 seconds, opens the box, stores the keys,
   publishes its record, and fetches the directory. Pairing is done.

The QR code is the trust channel. It must only be shown on screen and never logged.

## 9. Web Push wake-up

For a recipient with a push subscription and no live socket, the Hub sends a Web Push
(RFC 8030) with:

- VAPID authentication (RFC 8292, ES256, `sub` = the Hub URL; JWT `exp` 12 h, cached per
  push-service origin).
- An RFC 8291 `aes128gcm` encrypted payload `{"t":"wake"}`. This is never empty, because some
  distributors drop empty pushes.
- `Urgency: high` and `TTL: 86400`.

The Hub creates its VAPID P-256 key pair on first use and stores it in SQLite.

To save battery, the Hub sends at most one push per device until that device next fetches
(`GET /v1/messages` or a WebSocket connect), with a re-push allowed after 5 minutes.

When woken, a device calls `GET /v1/messages`, handles the messages, then sends `POST /v1/acks`.

## 10. Retention

- Each device has an ack cursor. A message is deleted once every recipient's cursor has
  passed it, or when `ttl_s` has passed, whichever comes first.
- `last_seen` is written at most once every 10 minutes per device. It is updated by
  authenticated HTTP requests, WebSocket connects and `ack` frames.
- Unclaimed pairings expire after 5 minutes. A pending device whose pairing expired is deleted.
- The Hub uses one alarm, scheduled for the earliest expiry.
